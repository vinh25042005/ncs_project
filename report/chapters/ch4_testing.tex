\section{Kiểm thử 1: Truy cập các cổng dịch vụ qua AWS NLB}
\subsection{Kịch bản kiểm thử}
Gửi các yêu cầu HTTP/HTTPS kiểm tra 5 cổng dịch vụ công khai qua AWS Network Load Balancer:
\begin{enumerate}
    \item Cổng 80: Ứng dụng web Online Boutique (HTTP).
    \item Cổng 443: Ứng dụng web Online Boutique bảo mật (HTTPS).
    \item Cổng 7443: Bảng điều khiển quản trị Rancher Server (HTTPS).
    \item Cổng 8443: Giao diện web giám sát an ninh Wazuh Dashboard (HTTPS).
    \item Cổng 31235: Giao diện trực quan hóa luồng mạng eBPF Hubble UI (HTTP).
\end{enumerate}

\subsection{Kết quả kiểm thử}
\begin{lstlisting}[language=bash, caption={Kết quả phản hồi HTTP từ các cổng dịch vụ}]

\section{Kiểm thử 7: Cân bằng tải và chuyển đổi dự phòng chéo vùng HAProxy (Cross-AZ Failover)}
\subsection{Kịch bản kiểm thử}
Bài kiểm thử thực nghiệm nhằm chứng minh năng lực phục hồi tự động của hệ thống khi đối mặt với sự cố phần cứng hoặc mạng tại từng nút (node failure) và kịch bản thảm họa phân mảnh chéo vùng (Cross-AZ Split Disaster):
\begin{enumerate}
    \item \textbf{Kịch bản 1 (Trạng thái bình thường)}: Kiểm tra tính thông suốt qua socket quản trị HAProxy trên cả hai Gateway và gửi yêu cầu HTTPS kiểm tra tải thông qua tên miền công khai AWS NLB.
    \item \textbf{Kịch bản 2 (Sự cố một Worker Node)}: Mô phỏng sự cố Worker 2 (\texttt{10.0.11.21} tại AZ-b) bị mất kết nối bằng cách chặn cổng 80 và 443 bằng IPTables DROP. Theo dõi thời gian HAProxy trên Gateway 2 phát hiện lỗi và chuyển hướng lưu lượng sang Worker 1 (\texttt{10.0.10.139} tại AZ-a).
    \item \textbf{Kịch bản 3 (Thảm họa kép chéo vùng - Gateway 1 và Worker 2 cùng sập)}: Mô phỏng thảm họa phức tạp nhất: Gateway 1 (AZ-a) dừng hoạt động hoàn toàn trong khi Worker 2 (AZ-b) vẫn đang gặp sự cố. Kiểm tra khả năng AWS NLB tự ngắt tải khỏi Gateway 1, chuyển toàn bộ lưu lượng sang Gateway 2, và Gateway 2 tự động chuyển tiếp chéo vùng sang Worker 1 duy nhất còn sống.
\end{enumerate}

\subsection{Kết quả kiểm thử}
\subsubsection{1. Trạng thái bình thường}
Kiểm tra số liệu thống kê qua Unix Socket quản trị \texttt{/run/haproxy/admin.sock} trên Gateway 1 và Gateway 2 cho thấy toàn bộ các nút backend đều được giám sát qua kiểm tra sức khỏe TCP chủ động (\texttt{check inter 2s rise 2 fall 2}) và đạt trạng thái \texttt{UP (L4OK)}:
\begin{lstlisting}[language=bash, caption={Trạng thái backend trên Gateway 1 và Gateway 2 qua UNIX Socket}]
# Tren Gateway 1:
echo "show stat" | sudo socat stdio /run/haproxy/admin.sock | awk -F',' '{printf "%-15s %-10s %-10s %-10s\n", $1, $2, $18, $37}'
# pxname          svname     status     check_status
http_nodes        worker1    UP         L4OK      
http_nodes        worker2    UP         L4OK      
http_nodes        BACKEND    UP                   
https_nodes       worker1    UP         L4OK      
https_nodes       worker2    UP         L4OK      
https_nodes       BACKEND    UP                   
rancher_nodes     master     UP         L4OK      

# Tren Gateway 2:
echo "show stat" | sudo socat stdio /run/haproxy/admin.sock | awk -F',' '{printf "%-15s %-10s %-10s %-10s\n", $1, $2, $18, $37}'
# pxname          svname     status     check_status
http_nodes        worker2    UP         L4OK      
http_nodes        worker1    UP         L4OK      
http_nodes        BACKEND    UP                   
https_nodes       worker2    UP         L4OK      
https_nodes       worker1    UP         L4OK      
https_nodes       BACKEND    UP                   
rancher_nodes     master     UP         L4OK      
\end{lstlisting}

\subsubsection{2. Sự cố Worker 2 và chuyển đổi dự phòng tại Gateway 2}
Tiến hành chặn gói tin cổng 80 và 443 trên Worker 2:
\begin{lstlisting}[language=bash]
# Tren Worker 2 (10.0.11.21):
sudo iptables -I INPUT 1 -p tcp --dport 80 -j DROP
sudo iptables -I INPUT 1 -p tcp --dport 443 -j DROP
\end{lstlisting}
Sau đúng 4 giây (2 chu kỳ kiểm tra $\times$ 2 giây), HAProxy trên Gateway 2 lập tức phát hiện sự cố kết nối TCP timeout và cô lập Worker 2, kích hoạt Worker 1 (node backup) gánh tải:
\begin{lstlisting}[language=bash, caption={Gateway 2 tự động phát hiện Worker 2 DOWN và kích hoạt Worker 1 Backup}]
echo "show stat" | sudo socat stdio /run/haproxy/admin.sock | awk -F',' '{printf "%-15s %-10s %-10s %-10s\n", $1, $2, $18, $37}'
# pxname          svname     status     check_status
http_nodes        worker2    DOWN       * L4TOUT  
http_nodes        worker1    UP         L4OK      
http_nodes        BACKEND    UP                   
https_nodes       worker2    DOWN       * L4TOUT  
https_nodes       worker1    UP         L4OK      
https_nodes       BACKEND    UP                   
\end{lstlisting}
Gửi truy vấn HTTPS trực tiếp tới địa chỉ công khai của Gateway 2 (\texttt{18.140.131.125}):
\begin{lstlisting}[language=bash]
curl -skI https://18.140.131.125/ | head -n 3
# Tra ve:
# HTTP/2 200 
# date: Fri, 06 Nov 2026 00:34:36 GMT
# content-type: text/html; charset=utf-8
\end{lstlisting}
Yêu cầu được chuyển tiếp xuyên qua mạng LAN Transit sang Worker 1 tại AZ-a thành công 100\%, chứng minh cơ chế Failover nội bộ hoạt động trơn tru.

\subsubsection{3. Thảm họa kép chéo vùng: Gateway 1 sập + Worker 2 sập}
Trong khi Worker 2 vẫn đang gặp sự cố, tiến hành dừng hoàn toàn tiến trình HAProxy trên Gateway 1:
\begin{lstlisting}[language=bash]
# Tren Gateway 1 (13.251.225.100):
sudo systemctl stop haproxy
\end{lstlisting}
Lúc này, Gateway 1 (AZ-a) và Worker 2 (AZ-b) cùng chết. AWS NLB nhận thấy Gateway 1 không còn phản hồi cổng 443, tự động chuyển toàn bộ yêu cầu của người dùng về Gateway 2. Tại Gateway 2, HAProxy tiếp tục chuyển tiếp lưu lượng chéo vùng sang Worker 1.

Thực hiện kiểm tra tính sẵn sàng bằng 5 yêu cầu liên tiếp qua tên miền công khai AWS NLB:
\begin{lstlisting}[language=bash, caption={Kết quả 5 yêu cầu liên tiếp qua AWS NLB trong kịch bản thảm họa kép}]
for i in {1..5}; do
  curl -s -k -o /dev/null -w "Request $i: HTTP Status %{http_code}, Remote IP: %{remote_ip}, Total time: %{time_total}s\n" \
    https://ncs-project-nlb-fa5afa04f4f63ce1.elb.ap-southeast-1.amazonaws.com/
done

# Ket qua ghi nhan:
# Request 1: HTTP Status 200, Remote IP: 13.251.75.133, Total time: 0.222785s
# Request 2: HTTP Status 200, Remote IP: 13.251.75.133, Total time: 0.216920s
# Request 3: HTTP Status 200, Remote IP: 13.251.75.133, Total time: 0.302685s
# Request 4: HTTP Status 200, Remote IP: 13.251.75.133, Total time: 0.237978s
# Request 5: HTTP Status 200, Remote IP: 13.251.75.133, Total time: 0.479905s
\end{lstlisting}

Toàn bộ 100\% các yêu cầu đều đạt mã phản hồi \textbf{HTTP/2 200 OK} với thời gian phản hồi trung bình chỉ $\sim 0.29\text{s}$. Hệ thống đạt độ tin cậy tuyệt đối, tự động vượt qua sự cố phân mảnh chéo vùng mà không cần bất kỳ sự can thiệp thủ công nào từ quản trị viên.

Sau khi mở khóa IPTables trên Worker 2 và khởi động lại HAProxy trên Gateway 1, toàn bộ các thành phần tự động kiểm tra sức khỏe và tái gia nhập cụm với trạng thái \texttt{UP (L4OK)} hoàn chỉnh.

\section{Kiểm thử 8: Giám sát an ninh Runtime Container với Falco và Falcosidekick UI}
\subsection{Kịch bản kiểm thử}
Thực hiện mô phỏng 3 hành vi tấn công trực tiếp tại tầng Runtime bên trong các Pod của ứng dụng Online Boutique:
\begin{enumerate}
    \item \textbf{Mở Shell tương tác trong Container sản xuất}: Thực thi lệnh spawn shell \texttt{/bin/sh} vào Pod \texttt{frontend}:
\begin{lstlisting}[language=bash]
kubectl exec -n online-boutique $(kubectl get pods -n online-boutique -l app=frontend -o jsonpath='{.items[0].metadata.name}') -- /bin/sh -c 'whoami; uptime'
\end{lstlisting}
    \item \textbf{Đọc trộm tập tin nhạy cảm của hệ thống}: Cố tình truy xuất tập tin \texttt{/etc/shadow} từ bên trong container:
\begin{lstlisting}[language=bash]
kubectl exec -n online-boutique $(kubectl get pods -n online-boutique -l app=frontend -o jsonpath='{.items[0].metadata.name}') -- cat /etc/shadow
\end{lstlisting}
    \item \textbf{Cài cắm tập tin thực thi vào thư mục nhị phân hệ thống}: Cố gắng ghi tệp tin độc hại vào thư mục \texttt{/bin}:
\begin{lstlisting}[language=bash]
kubectl exec -n online-boutique $(kubectl get pods -n online-boutique -l app=frontend -o jsonpath='{.items[0].metadata.name}') -- touch /bin/malicious_backdoor
\end{lstlisting}
\end{enumerate}

\subsection{Kết quả kiểm thử}
\subsubsection{1. Nhật ký sự kiện bắt giữ bởi Falco eBPF Driver}
Ngay khi các hành vi trên được kích hoạt, Falco thông qua driver \texttt{modern\_ebpf} phát hiện các system call (\texttt{execve}, \texttt{openat}) bất thường và xuất cảnh báo JSON thời gian thực:

\subsubsection{2. Trực quan hóa cảnh báo an ninh trên Falcosidekick Web UI}
Falcosidekick daemon nhận luồng stream cảnh báo qua cổng HTTP 2801 và đẩy lên giao diện Falcosidekick Web UI tại cổng NodePort \textbf{31802}:
\begin{lstlisting}[language=bash, caption={Kiểm tra trạng thái sẵn sàng của giao diện Falcosidekick Web UI}]
curl -sI http://10.0.10.10:31802/ | head -n 2
# Phản hồi:
# HTTP/1.1 200 OK
# Content-Type: text/html; charset=utf-8
\end{lstlisting}
Trên trang quản trị Falcosidekick UI (\texttt{http://10.0.10.10:31802}):
\begin{itemize}
    \item Biểu đồ hình tròn và biểu đồ cột thống kê trực quan số lượng vi phạm được phân tách rõ theo các cấp độ nghiêm trọng: \textbf{Critical} (Ghi file vào thư mục nhị phân), \textbf{Error} (Đọc file nhạy cảm), và \textbf{Warning} (Mở shell tương tác trái phép).
    \item Bảng chi tiết sự kiện cho phép lọc nhanh theo Namespace \texttt{online-boutique}, hiển thị đầy đủ tên Pod vi phạm (\texttt{frontend}), ID container, thời điểm kích hoạt và mã lệnh tấn công, giúp các chuyên gia SOC rút ngắn tối đa thời gian phát hiện và ứng phó sự cố (MTTD \& MTTR).
\end{itemize}
